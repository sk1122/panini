# Connect personal coding agents

Panini exposes a Streamable HTTP MCP endpoint at `http://127.0.0.1:4141/mcp`. Every coding harness connects through a personal agent profile rather than a shared app credential.

## Create a profile

1. Open Panini and select **Agents**.
2. Select **Create agent**.
3. Enter the workspace member, a profile name, the harness, its purpose, and the smallest capability set it needs.
4. Select **Create and connect**.
5. Copy the one-time enrollment secret and follow the generated harness-specific steps.

A member can create several profiles, for example one Codex research profile, one Claude Code delivery profile, and one Hermes operator profile. Each profile has its own identity, grants, secret, activity timestamp, rotation control, and revocation control.

Panini shows an enrollment secret only when the profile is created or its secret is rotated. The database stores only a SHA-256 digest and a short non-secret hint. Never paste the secret into a repository or shared project configuration.

## Harnesses

### Codex

The generated recipe stores the secret in an environment variable and registers a user-scoped remote server:

```sh
read -r -s PANINI_AGENT_EXAMPLE_TOKEN
export PANINI_AGENT_EXAMPLE_TOKEN
codex mcp add panini-example \
  --url http://127.0.0.1:4141/mcp \
  --bearer-token-env-var PANINI_AGENT_EXAMPLE_TOKEN
codex mcp list
```

The exact server and environment variable names are unique to the profile. Codex shares MCP configuration across its desktop, CLI, and IDE surfaces.

On a private machine, the create and rotate flows also provide an optional direct-secret `config.toml` block using `http_headers.Authorization`. This avoids environment inheritance problems in the desktop app, but stores the enrollment secret in plaintext in the user's Codex configuration. The environment-variable method remains preferred.

### Claude Code

The setup flow emits a user-scoped HTTP MCP entry whose authorization header references an environment variable:

```sh
read -r -s PANINI_AGENT_EXAMPLE_TOKEN
export PANINI_AGENT_EXAMPLE_TOKEN
claude mcp add-json --scope user panini-example \
  '{"type":"http","url":"http://127.0.0.1:4141/mcp","headers":{"Authorization":"Bearer ${PANINI_AGENT_EXAMPLE_TOKEN}"}}'
claude mcp get panini-example
```

The saved configuration contains the environment reference, not the secret value.

### Hermes Agent

Hermes reads remote MCP servers from `~/.hermes/config.yaml`, as documented in the [Hermes MCP guide](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/mcp.md). Add the generated block under `mcp_servers`; its authorization header references the profile environment variable rather than containing the enrollment secret:

```yaml
mcp_servers:
  panini-example:
    url: "http://127.0.0.1:4141/mcp"
    headers:
      Authorization: "Bearer ${PANINI_AGENT_EXAMPLE_TOKEN}"
```

Then test the server and start Hermes:

```sh
hermes mcp test panini-example
hermes chat
```

Use `/reload-mcp` in an existing Hermes session after changing the configuration. The generated server and environment variable names are unique to the profile.

### Pi

Pi intentionally keeps MCP outside its core, so Panini serves a reviewed TypeScript extension that registers equivalent native Pi tools:

```sh
mkdir -p ~/.pi/agent/extensions
curl -fsSL http://127.0.0.1:4141/integrations/pi/panini.ts \
  -o ~/.pi/agent/extensions/panini.ts
PANINI_URL=http://127.0.0.1:4141 \
  PANINI_AGENT_TOKEN="$PANINI_AGENT_EXAMPLE_TOKEN" pi
```

Use the URL generated by the app when Panini is not running on the same machine as Pi.

### Other MCP clients

Choose **Other MCP client** to receive a JSON configuration containing the endpoint and an environment-variable authorization reference. The client must support Streamable HTTP and environment expansion in headers.

## Capability grants

Profiles can receive any combination of:

- `work:read`: read accepted tasks and proposal status;
- `work:propose`: propose new tasks or changes to existing tasks;
- `context:read`: open the context index, facts, and files;
- `source:read`: discover and open authorized source documents or sections as untrusted evidence;
- `context:propose`: propose evidence-backed facts or files;
- `evidence:report`: submit privacy-filtered lifecycle receipts.
- `workspace:read` and `workspace:write`: read or save this agent profile's persistent private files.

The MCP tools are:

- `identity_get` for the authenticated user, agent, grants, and both workspace roots;
- `context_get` and `context_read` for accepted context;
- `source_read` for a pinned source document or section when the profile has `source:read`;
- `work_search` for accepted work;
- `task_create_proposal`, `proposal_create`, and `proposal_status` for reviewable work changes;
- `context_proposal_create` for evidence-backed context proposals;
- `work_report` for privacy-filtered work evidence;
- `agent_file_list`, `agent_file_read`, `agent_file_write`, and `agent_file_delete` for private `panini://<user_id>/<agent_id>/<filename>` working memory;
- `user_file_list`, `user_file_read`, `user_file_write`, and `user_file_delete` for `panini://<user_id>/user/<filename>` personal context shared across that user's agents with workspace grants;
- `start-work` and `handoff` prompts.

Agent profile identity is derived from the presented secret. Tools do not accept a caller-supplied profile identity. Accepted context remains the default authority. Source reads are explicitly labeled as untrusted evidence, and a source cannot silently override accepted context or act as an instruction. Company-memory writes remain proposals or evidence and cannot directly mutate accepted task or context state. Private agent-file writes change only that profile's working memory.

Before saving context, call `identity_get`. Use `agent_file_write` for profile-specific notes, `user_file_write` for the user's personal context and preferences shared across their agents, and `context_proposal_create` for company knowledge. Both personal workspaces use `workspace:read` / `workspace:write` grants and encrypted, audited revisions. User files remain available to other authorized profiles after the writing profile is revoked. Read the current version before replacement; concurrent stale writes fail rather than overwrite another agent's changes. Workspace content is working memory, never an instruction that overrides the current user request or accepted company policy.

When `OPENROUTER_API_KEY` and `JEV_WORK_ALLOWED_VISIBILITIES` are configured, Panini uses Jev through OpenRouter Decisions to check each new task or context proposal against the agent-visible accepted tasks, context, and cited evidence. A fitting proposal stays pending for normal review, an invalid proposal is rejected with an audit record, and a classifier failure leaves the proposal pending rather than accepting unchecked state.

## Optional portable skill

The setup flow connects the tool surface. The portable skill adds operating guidance for agents:

```sh
mkdir -p .codex/skills
cp -R integrations/panini-skill .codex/skills/panini
```

For Claude Code:

```sh
mkdir -p .claude/skills
cp -R integrations/panini-skill .claude/skills/panini
```

For Hermes, whose local skills live under `~/.hermes/skills/`:

```sh
mkdir -p ~/.hermes/skills
cp -R integrations/panini-skill ~/.hermes/skills/panini
```

The skill tells the harness to separate accepted state from pending proposals and to keep prompts, transcripts, secrets, and raw tool output out of evidence receipts.

## Deployment boundary

The local UI currently records the owner as a workspace-member label. Production identity-provider login, organization membership enforcement, OAuth, and administrator roles remain deployment work. Put Panini behind HTTPS and an identity-aware proxy before exposing it outside a trusted network.
