# GitHub connection options for Panini

Researched against current GitHub documentation on 2026-09-20. This is an external API design note, not a claim that Panini has implemented or tested the flow.

## Recommendation

Use a **GitHub App installation** as the durable connection to an organization or selected repositories. GitHub recommends Apps over OAuth Apps for fine-grained permissions, repository selection, short-lived tokens, installation-owned automation, a central webhook, and an installation rate limit that can scale. An OAuth App would act through a user's grant, need separately managed repository or organization hooks, and is mainly preferable if enterprise-level resources are required. Panini's described repository activity use case does not require those enterprise-level resources. [GitHub App vs OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)

The minimum useful registration for commits, branches, pull requests, reviews, checks, statuses, and issues is repository **Metadata: read** (implicit for Apps), **Contents: read**, **Pull requests: read**, **Checks: read**, **Commit statuses: read**, and **Issues: read**. Request no write permission for read-only ingestion. Register only the events Panini will consume. GitHub maps event availability to App permissions, and permission increases for existing installations require the account owner's approval. [Choosing App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [App best practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)

## Connection and discovery

1. The user starts the GitHub App install flow and chooses an account and all or selected repositories. An organization owner can install; repository admins can install for repositories they administer when the App does not request organization resources or repository administration permission, subject to organization policy. The install grants access to the account's selected resources. [Installing a GitHub App](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party), [organization programmatic access](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/about-programmatic-access-in-your-organization)
   To try showing the user's organizations **before** installation, use a separately authorized GitHub App user token with `GET /user/memberships/orgs?state=active`; test this with the actual organization, and fall back to GitHub's installation chooser if the pre-installation list is unavailable. GitHub says `GET /user/orgs` can return an empty list for fine-grained tokens. Also, enabling GitHub's automatic “Request user authorization (OAuth) during installation” removes the ability to configure a setup URL, so a design that needs both should run OAuth separately. [Organization memberships](https://docs.github.com/en/rest/orgs/members#list-organization-memberships-for-the-authenticated-user), [organization-list caveat](https://docs.github.com/en/rest/orgs/orgs#list-organizations-for-the-authenticated-user), [App registration](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration)
2. GitHub can redirect to a setup URL with `installation_id`. **Do not trust that parameter alone**: GitHub warns it can be spoofed. If linking an installation to an initiating Panini user, use a GitHub App user authorization flow and verify that `GET /user/installations` includes that installation, then persist the verified installation ID, account identity, and selected repository IDs. The GitHub App's web authorization flow supports `state` and strongly recommends PKCE. A GitHub App user token can list only installations and repositories the user can explicitly access; `GET /user/installations/{installation_id}/repositories` gives the user's accessible subset. [Setup URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url), [user token flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), [installation endpoints](https://docs.github.com/en/rest/apps/installations)
3. Once linked, background ingestion should use an **installation access token**, not the connecting user's token. The server signs a JWT with the App private key and exchanges it for an installation token; that token expires after one hour and can be narrowed to repositories and permissions already granted. `GET /installation/repositories` lists the installation's current repository access. `GET /app/installations` lists all installations to the authenticated App. The installation continues to work if the installer leaves the organization. [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), [installation endpoints](https://docs.github.com/en/rest/apps/installations), [App endpoints](https://docs.github.com/en/rest/apps/apps), [GitHub App vs OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)
4. User authorization is optional for ongoing installation-owned reads, but useful for linking the installer, login, or future user-attributed actions. It is a distinct grant: each member must authorize before Panini acts as that member. A user token is limited by both the App's permissions and the user's permissions. Expiring user tokens last eight hours, with six-month refresh tokens when enabled; an installation token lasts one hour. [On behalf of a user](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user), [refreshing user tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens), [installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)

## Read permissions and events

| Activity | Read permission and initial webhook subscription | REST backfill/reconciliation |
| --- | --- | --- |
| Commits and branches | **Contents: read**; `push` (commit/ref updates), plus `create` and `delete` if Panini needs explicit branch/tag lifecycle events. `push` also covers branch deletion. | List commits and branches with Contents read. A `push` payload contains at most 2,048 commits, so fetch more when needed. [Events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [commits](https://docs.github.com/en/rest/commits/commits), [branches](https://docs.github.com/en/rest/branches/branches) |
| Pull requests and reviews | **Pull requests: read**; `pull_request`, `pull_request_review`; add `pull_request_review_comment` and `pull_request_review_thread` only if individual discussion activity matters. | List pull requests and reviews with Pull requests read. [Events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [pull requests](https://docs.github.com/en/rest/pulls/pulls), [reviews](https://docs.github.com/en/rest/pulls/reviews) |
| CI checks and legacy commit statuses | **Checks: read** for `check_run` or `check_suite`; **Commit statuses: read** for `status`. These are distinct surfaces. | List check runs for a ref with Checks read and combined commit status with Commit statuses read. [Events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [check runs](https://docs.github.com/en/rest/checks/runs), [commit statuses](https://docs.github.com/en/rest/commits/statuses) |
| Issues | **Issues: read**; `issues`, and `issue_comment` if comments matter. | List repository issues with Issues read; GitHub's Issues REST endpoints also return pull requests, identifiable by the `pull_request` key. [Events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [issues](https://docs.github.com/en/rest/issues/issues) |
| Installation scope | `installation`, `installation_repositories`, and `github_app_authorization` are default App events. | Refresh the accessible repository list when scope changes; stop user-token calls after authorization revocation. [Events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [installation endpoints](https://docs.github.com/en/rest/apps/installations) |

## Ingestion limits and safety

- Backfill each selected repository with paginated REST reads; GitHub's default page is often 30 and most endpoints allow up to 100. Follow `Link: rel="next"` rather than assuming page counts. Preserve a cursor/checkpoint per repository and entity; reconcile after webhook gaps. This checkpoint design is a Panini inference from the documented pagination and delivery behavior. [Pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api), [failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)
- Prefer webhooks over polling. Installation REST tokens start at 5,000 requests/hour (15,000 for Enterprise Cloud organizations); non-Enterprise installations can scale by users/repositories to 12,500. Secondary limits also apply. Watch rate-limit headers, `Retry-After`, and reset time; back off when limited. [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [App best practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)
- Verify the raw request against `X-Hub-Signature-256` with a high-entropy webhook secret and constant-time comparison; use HTTPS. Check `X-GitHub-Event` and the action. Deduplicate on `X-GitHub-Delivery` (redelivery keeps the same ID), durably queue work, and respond `2xx` within 10 seconds. [Validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), [webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)
- GitHub does **not** automatically redeliver failures. Track failed App webhook deliveries and explicitly redeliver or reconcile; a server timeout past 10 seconds counts as failure. App uninstall disables its webhook access, while authorization revocation is distinct from uninstall. Handle `installation`/`installation_repositories` changes as access changes and stop ingestion for removed repositories. [Failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries), [App vs OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps), [events](https://docs.github.com/en/webhooks/webhook-events-and-payloads)
- GitHub has explicit event gaps: `push` is absent when more than 5,000 branches are pushed at once; tag and payload size caps can also suppress events. A `push` payload caps its commits at 2,048. Reconciliation is therefore necessary even with healthy webhook delivery. [Webhook events and payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads)

No GitHub App was registered, installed, or tested for this note. The exact permission set should be trimmed to the activity Panini actually decides to ingest before registration.
